# 兰剑机器人团队联调指南

本文面向通过 Git 获取 BlueSword-Gateway 的机器人团队，说明从安装到真实机器人联调的操作。接口字段以[接口文档](接口文档.md)为准；其中路径、回调及响应格式仍是待双方确认的对接草案。本文说明当前代码行为，不代表真实机器人联调已经通过。

## 1. 获取代码并构建

准备 Git、Node.js 24.13.0 或以上版本、pnpm 11.25.0。在 PowerShell 中执行以下命令；将占位地址替换为项目负责人提供的可访问仓库地址。目前作者工作区没有配置远程地址，具体地址及访问权限需另行提供。

```powershell
git clone <负责人提供的仓库地址> BlueSword-Gateway
Set-Location BlueSword-Gateway
git branch --show-current
git rev-parse HEAD
node --version
pnpm.cmd --version
pnpm.cmd install --frozen-lockfile
pnpm.cmd build
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

负责人当前整理代码的分支为 `main`，以实际交接分支和提交号为准。请记录实际提交号，双方使用同一版本排查。Git 不包含依赖、已构建网页、密钥和数据库，首次拉取后必须安装并构建；不要直接跳到启动。缺少 pnpm 时，可在 Node/npm 已安装的终端运行 `npm.cmd install --global pnpm@11.25.0`，重新打开终端后核对版本。若 PowerShell 执行策略拦截 `pnpm`，使用上述 `pnpm.cmd`。

后续更新前，先正常停止服务并核对本地修改；工作区干净时执行 `git pull --ff-only`，再执行安装和构建命令。保留已有 `.env` 及 `.data/`，不要重新覆盖配置或删库清任务。不知道如何保留本地修改时先联系负责人，不强制覆盖。

## 2. 配置真实机器人

建议网关与机器人部署在同一局域网。双方先交换机器人任务接收完整 URL，以及机器人能够访问的网关 IP 和端口；同时核对物品名称、位置和数量。UU、SSH 等远程操控方式本身不能代替 HTTP 双向连通。

编辑根目录 `.env`，以下为配置示意，地址和工作人员凭据必须替换：

```dotenv
PORT=4100
BOOTH_HOST=0.0.0.0
BOOTH_ROBOT_MODE=http
ROBOT_DISPATCH_URL=http://<机器人IP>:<端口>/api/task/dispatch
ROBOT_TIMEOUT_MS=8000
BOOTH_CATALOG_PATH=config/booth-catalog.example.json
BOOTH_CATALOG_CONFIRMED=false
BOOTH_DB_PATH=.data/booth.sqlite
BOOTH_OPERATOR_TOKEN=<由现场负责人设置的工作人员凭据>
```

先核对 `BOOTH_CATALOG_PATH` 对应 JSON 中的 `name`、`location`、`maxCount`（每单上限）、`initialStock`（初始化及补满目标）。可复制示例为现场目录并调整路径。核对实物与双方取值一致后，将 `BOOTH_CATALOG_CONFIRMED` 改为 `true`；未确认时禁止发单。示例库存为矿泉水3、小面包3、纪念品2、蔬菜礼盒1，不代表现场实际库存。

启动只需一个网关终端：

```powershell
pnpm.cmd serve
```

在运行电脑打开 `http://127.0.0.1:4100`。其他设备及机器人使用 `http://<网关电脑实际IP>:4100`；`0.0.0.0` 是监听设置，`127.0.0.1` 只指访问者自己的电脑，两者都不能作为另一台设备的网关地址。网页和回调共用4100端口。保持进程和电脑在线，停止时按 Ctrl+C；修改 `.env` 后重启生效。同一数据库只运行一个网关进程。

## 3. 开启 AI 对话

系统支持 AI 对话，但 Git 不提供任何真实密钥。需要聊天时，由现场负责人在 `.env` 填写所选供应商的有效配置。以下 DeepSeek 示例可直接按项目配置字段填写；模型名沿用现场有效账号的实际配置：

```dotenv
BOOTH_AI_PROVIDER=deepseek
DEEPSEEK_API_KEY=<现场提供的有效密钥>
DEEPSEEK_MODEL=deepseek-flash
```

如使用 OpenAI，则设置 `BOOTH_AI_PROVIDER=openai`，填写 `OPENAI_API_KEY`、`OPENAI_MODEL` 和适用的 `OPENAI_BASE_URL`，字段见 `.env.example`。供应商一次只选择一家，不自动切换。启动终端已有的同名环境变量优先于 `.env`，切换时须核对旧变量；密钥只留在服务端，不发到群聊、不提交 Git。

重启网关后，先问“这里有什么？”确认能回复，再测试选物品。聊天框显示“助手暂不可用，可直接选物品”表示服务没有加载到所选供应商的密钥；工作人员页可查看供应商、模型及凭据配置状态。已配置不等于调用成功，仍需有效账号和模型服务网络。没有密钥也能手选验证机器人接口。

聊天只建议物品与数量，用户点击“确认取物”才发单。逐字展示的出发、抓取、返回是预设模拟过程，不来自机器人实时中间反馈，也不用于判断完成；实际完成必须由机器人通知。

## 4. 双方接口与报文

均使用 POST 和 `Content-Type: application/json`。机器人只需实现任务接收，并向网关发送完成或不可恢复故障通知，无需启动项目中的模拟器或实现细粒度步骤接口。当前三个机器人接口没有代码级鉴权，工作人员凭据也不保护它们；应在双方受控可达网络内联调，若需公网对接须先约定网络访问保护。

| 方向 | 地址 | 内容 |
| --- | --- | --- |
| 网关 → 机器人 | `.env` 中 `ROBOT_DISPATCH_URL`，建议路径 `/api/task/dispatch` | `{"location":"货架1-2层","item":"矿泉水","count":1}` |
| 机器人 → 网关 | `http://<网关IP>:4100/api/task/finished` | `{"result":"success"}` |
| 机器人 → 网关 | `http://<网关IP>:4100/api/task/error` | `{"message":"机械臂故障，无法自动恢复"}` |

下发只有 `location`、`item`、`count` 三个字段。机器人应立即返回是否受理，例如 `{"code":1,"data":"received","success":true}`，不能受理则返回 `success:false` 及原因；网关不根据 `code:1` 判断成功。机器人在受理回复完成后再上报最终结果；不要将下发请求一直保持到实物取回。默认受理等待期限为8秒，超时或反馈不明确时网关保留占用，不自动重发。

机器人完成任务并放下物品后，才调用 finished。当前实现也接受空 JSON 或空请求体作为完成通知；统一使用表中的明确 JSON 便于核对。不可自行恢复的故障调用 error，`message` 为非空且不超过1000字的说明；可自行恢复的问题由机器人内部处理。网关成功接收两类通知时回复 `{"code":1,"data":"OK","success":true}`，请检查 HTTP 状态及响应，异常时保留原始通信记录。

当前没有任务关联字段，不能可靠识别上一单迟到到下一单的通知。双方须在联调前核对重复、延迟和重发规则；不要在下一单开始后重发上一单通知。增加 `taskId` 的[建议方案](task-id-proposal.md)尚未实施，不能直接向当前接口加入该字段。一次只允许一单并不能消除迟到通知风险。

## 5. 真实联调顺序

1. 从机器人一侧访问 `http://<网关IP>:4100/api/health`，应返回 `ok:true`；从网关电脑核对能访问机器人实际端口。健康检查只证明网关进程可达，不证明机器人能执行。网络不通先核对 IP、端口、路由和访问规则，不通过反复发真实任务来探测。
2. 在网页手选1件有库存的物品并确认，核对机器人收到的三个字段。机器人回复受理后，网页应继续等待，不能提前显示取好了。
3. 实际完成并放下物品后，机器人发送完成通知。检查回执、页面结束思考及完成回复；右上角约10秒后恢复等待选择，聊天和任务记录保留。
4. 在双方约定的受控条件下分别验证明确拒绝和不可恢复故障。拒绝退回预留库存；故障保持占用且不能再发单，须现场核对后处理。不要为测试故障制造危险动作。
5. 核对单个及全部补货重置，停止并重启网关确认库存和记录保留。再开启 AI，验证聊天推荐、超量说明及用户确认后才发单。

记录测试时间、双方软件版本/网关提交号、实际地址、任务物品数量、请求/响应、页面结果及未通过项；不要把模拟器通过写成真实机器人通过。需要先自测或看原始报文时，按[人工测试指南](manual-interface-test.md)运行两个本机终端：4101为网关，4201为手动受理/通知的机器人模拟器。真实机器人联调用本节的 `pnpm.cmd serve`，不用4201，也不用会自动完成的 `pnpm dev:demo`。

## 6. 工作人员补货与异常处理

入口为 `http://<网关IP>:4100/#operations`，凭据使用 `.env` 中现场设置的 `BOOTH_OPERATOR_TOKEN`。日常访客页面不显示固定入口，工作人员可收藏地址。

- **库存不足**：确认任务时预留数量，完成后视作已取走。例如水取完3瓶后不能继续选。重启及“开始新体验”不会补满，修改 `initialStock` 也不会覆盖已有剩余数量。
- **单个补货**：实际补满后，输入凭据，在“补货重置”选择物品，核对当前数及补满目标，勾选“已核对并补满所选物品”，点击“重置所选物品库存”。
- **全部补货**：全部实物都补满后选择“全部物品”，逐项核对目标，勾选“已核对并补满全部物品”，点击“重置全部物品库存”。成功后所有数量一起恢复，任务记录保留，其他页面同步。
- **按钮灰色**：需要凭据、相应补货勾选、状态同步正常，并且没有未结束任务或告警。成功后凭据和勾选清空，按钮再次变灰属于正常行为；切换范围或库存变化后须重新确认。
- **故障或受理不明**：先现场确认机器人停止及物品情况，输入凭据、勾选“已现场核对机器人停止及物品情况”，再点击“解除本地占用”。这不会停止机器人，也不会恢复库存；需要补货时再单独操作。执行中的任务不能从我方页面取消，请联系机器人负责人。

当前任务详情中的状态不代表机器人提供了细粒度实时遥测。数据库位于配置的 `BOOTH_DB_PATH`；任务和库存需要持续保留，不删除或更换数据库来解除限制。更完整的数量处理见[库存说明](booth-inventory.md)。
