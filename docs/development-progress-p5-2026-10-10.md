## Claude Code 第二版建议的独立复核

复核依据为正式接口文档 §2–§3、开发计划 P1/P3/P6，以及当前 UUID 任务记录、回调事务、占用和人工解除逻辑。第二版由用户提供，未获得机器人团队确认。

已证实事实：机器人报文没有关联标识，网关按通知到达时的活动任务更新；P1 的 HTTP 替身测试复现了跨单误关联。内部任务 ID 已使用 randomUUID 生成并写入 SQLite；它尚未成为机器人 taskId。回调审计与业务状态已同事务提交，提交成功后才返回成功回执。故障和受理不明保持占用，工作人员人工解除不会调用机器人取消接口；执行中任务不能从现有入口解除。

合理假设：重复通知、跨单迟到、回执丢失、服务重启和完成/故障互相矛盾，都适合作为防御性设计场景。它们不能表述为机器人已实施的行为，也不能凭“分布式系统标准实践”证明具体重试策略或持久化能力。

技术建议：采用持久化的稳定 UUID 作为关联标识，机器人原样返回，适合当前一条完整取送任务。可以评估复用现有内部任务 ID，避免两套标识不必要地分离；相同请求核对或通知重试时不能重新生成标识。仅有 UUID 仍不足以可靠处理重复和冲突，需要明确每种状态允许的转移及人工核对路径。

第二版“单任务串行 + 超时强制收尾”这一名称有误导性。可执行的临时边界是串行占用、超时提醒、现场核对；时间到了不能自动完成、自动解锁或重发任务。若要让长时间执行中任务在人工确认后解除，还需明确核对规则并调整内部操作准入，现有入口并不支持该状态。人工解除后上一单迟到通知仍可能影响下一单，等待窗口或串行锁不能可靠消除这一残余风险。

以下为技术建议，尚不是正式协议：

| 场景 | 建议的处理边界 | 仍需确认 |
| --- | --- | --- |
| 未知 taskId | 持久化隔离审计，不改变当前业务状态，进入人工核对。 | 持久化隔离是否足以返回成功、是否应继续重试、隔离记录的处理责任。成功回执可能让对方停止重发，不能默认丢弃。 |
| 相同通知重复 | 每次接收可审计，已确认结果不重复触发副作用或释放别的任务。 | 如何识别相同事件、重复回执格式；无标识报文无法跨任务去重。 |
| 完成与故障冲突 | 保留两个事实，标记异常并人工核对，不单纯按到达顺序覆盖终态。 | 哪个状态保持占用、是否需要事件序号、人工裁决与对外回执。 |
| 写入/提交失败 | 网关不确认成功，不发布未提交状态；由发送方依约重试。 | 重试次数、间隔、耗尽与告警规则。 |
| 已提交但回执丢失 | 不回滚已提交事实；再次接收应安全确认相同结果。 | 机器人成功判定、重发持久化和去重约定。 |
| 收尾与下一单 | 区分通知收到、机器人物理收尾、故障核对与允许下一单。 | 机器人是否已安全停止、何时可接单及并发能力；不能仅由网关自行选择。 |

三个接口新增 taskId、字段是否必填、回执是否回传、旧报文兼容、未知/冲突通知响应和收尾条件，都需要双方确认并更新正式文档。当前不实施这些契约变化，也不向机器人团队作出承诺。当前完成通知能够覆盖故障任务的行为并未因为这次审查自动改变，它仍属于待确认的冲突处理范围。

OpenAI 保留 Responses 接口、gpt-4.1-mini 默认模型与 strict JSON schema；DeepSeek 使用 Chat Completions、JSON object 输出，默认 deepseek-flash 并显式关闭思考模式。该默认模型依据本次查阅的 [DeepSeek 模型与计费说明](https://api-docs.deepseek.com/quick_start/pricing/) 和 [Chat Completions 参考](https://api-docs.deepseek.com/api/create-chat-completion/)；没有沿用未经核对的历史模型别名。OpenAI 行为依据 [模型说明](https://developers.openai.com/api/docs/models/gpt-4.1-mini) 和 [结构化输出说明](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)。依赖版本未变。

两家输出均校验完整结构、目录 ID、整数数量及该物品上限，拒绝额外字段、截断、拒绝和非 JSON 响应。每次模型调用生成内部请求 UUID，日志仅记录供应商、配置模型、耗时、上游 HTTP 状态、结果与错误类别；不记录密钥、请求头、上游正文或完整对话。时间预算包括请求和正文读取，慢正文取消后仍可继续提问。模型建议不调用机器人。
