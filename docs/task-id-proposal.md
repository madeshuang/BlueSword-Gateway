# 机器人 taskId 关联建议

**建议方案，待机器人团队确认。** 本文补充[接口文档第 3 节第 4 项](接口文档.md#3-待确认)，没有改变当前正式报文或机器人适配代码，也未经过真实机器人联调。

建议复用网关在发送前保存的内部 `BoothTask.id`（UUID），作为双方的 `taskId`。下发任务在原有 `location`、`item`、`count` 之外增加 `taskId`；完成、不可恢复故障等任务通知必须原样返回该值。例如：

| 报文 | 建议请求体 |
| --- | --- |
| 下发 | `{ "taskId": "<同一任务UUID>", "location": "货架1-2层", "item": "矿泉水", "count": 1 }` |
| 完成 | `{ "taskId": "<同一任务UUID>", "result": "success" }` |
| 故障 | `{ "taskId": "<同一任务UUID>", "message": "机械臂故障，无法自动恢复" }` |

网关只查询并更新与通知 `taskId` 精确匹配的已保存任务。缺少、无效或找不到 `taskId` 时，应记录异常并交由工作人员核对，不能猜测归属，更不能改写当前活动任务。具体 HTTP 拒绝码及回执仍需双方确认。重复通知、相互矛盾的通知、已结束任务再次收到通知的处理规则，也需先约定；匹配到任务并不意味着可以无条件改写状态。

建议同一任务重试仍使用原 `taskId`，但这不等于机器人已经支持重复指令只执行一次；执行防重、重发规则、受理回执是否回显 `taskId`、字段何时改为必填及旧版迁移方式，均待机器人团队确认。

`requestId` 仍用于前端确认取物的防重；体验凭据用于核实当前聊天可查询哪个任务。它们不能替代机器人通知中的 `taskId`。当前无标识回调仍可能把上一单的迟到通知作用于下一单（P1）；本批未修复，后续须根据双方确认的协议实施并验证。
