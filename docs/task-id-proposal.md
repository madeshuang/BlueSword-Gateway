# 机器人 taskId 关联建议

**建议方案，待机器人团队确认。** 本文补充[接口文档第 3 节第 4 项](接口文档.md#3-待确认)，没有改变当前正式报文或机器人适配代码，也未经过真实机器人联调。

目前机器人通知没有任务标识，上一单的通知如果延迟到达，可能被误认为是当前任务的结果。建议增加唯一的 `taskId`，让网关能够确认通知属于哪一次取物。

网关下发任务时，在原有 `location`、`item`、`count` 之外增加 `taskId`，使用网关已有的任务编号。机器人在完成、故障等任务通知中原样返回收到的 `taskId`，不要重新生成或修改。例如：

| 报文 | 建议请求体 |
| --- | --- |
| 下发 | `{ "taskId": "<同一任务UUID>", "location": "货架1-2层", "item": "矿泉水", "count": 1 }` |
| 完成 | `{ "taskId": "<同一任务UUID>", "result": "success" }` |
| 故障 | `{ "taskId": "<同一任务UUID>", "message": "机械臂故障，无法自动恢复" }` |

按此建议，网关只更新与通知中的 `taskId` 对应的任务。通知缺少编号或找不到对应任务时，交由工作人员核对，不将它当作当前任务的结果。

请机器人团队确认：

- 下发接口能否接收 `taskId`，完成、故障通知及接单回复能否原样返回？示例中的字段及格式是否适用？
- 同一任务重发时是否沿用原 `taskId`，机器人如何避免重复执行？
- 缺少或无法识别 `taskId`，以及通知重复或结果冲突时，双方如何处理和回复？
- 何时启用该字段，是否设为必填，旧版报文如何过渡？

以上均待机器人团队确认后再实施和验证；目前迟到通知可能影响下一单的问题尚未解决。
