# 2026-10-12 初版演示与接口讨论准备

初次核对日期：2026-10-11；演示操作与已验证范围于 2026-10-12 更新。演示使用本机 Microsoft Edge，目标是展示我方可运行的初版并收集机器人团队反馈。本文依据当前工作区、既有测试、原始会议和在线 Issue 整理，不是机器人协议承诺或最终验收报告。正式接口继续以 [接口文档](接口文档.md) 为准。

## 先记住这几句话

“今天展示的是用户选择、确认、等待通知和异常核对的完整交互。机器人对端是本地模拟器；模型是否真实调用，另行说明。系统不会把受理当成完成，也不会展示机器人没有上报的导航、抓取步骤。”

“接口最需要确认的是：上一单的通知会不会在下一单开始后到达；如果会，我们怎样知道它属于哪一单。任务编号是推荐办法，但如果不加编号，需要机器人侧提供能核对的通知隔离保证。”

“语音在早期会议里确实提过，但没有列入当前 10 月 12 日初版验收。本次先演示文字和手动选择，语音后续作为输入增强评估，仍须由用户确认才能发单。”

现在需要确定演示主线、模型调用口径和异常展示范围。通知重试参数、任务关联字段、正常耗时和故障收尾可以在会议中讨论、真实联调时验证，不需要今晚全部定案；未确认前，不承诺可靠连续真实多单运行。

## 约五分钟的本地模拟演示

启动前先按 [初版交接说明](initial-demo-handoff.md) 检查 Node/pnpm、4100/4200/5173 端口、演示数据库和供应商配置。建议沿用 DeepSeek 官方已有小样本证据的配置；启动方式如下，现有密钥由本地文件加载，不展示或复制：

```powershell
$env:BOOTH_AI_PROVIDER = 'deepseek'
pnpm dev:demo
```

访问 [本机演示页](http://127.0.0.1:5173)，Vite 如改用其他端口，以启动输出为准。此命令加载 `.env`；该组合已实际启动，目前继续沿用运行服务并通过热更新检查，演示前仍应亲自走一次完整流程。它使用示例目录和独立演示库，不连接现场机器人。选定供应商缺少凭据时，助手输入禁用，仍可手动选品；存在凭据也不证明余额、网络或模型正常。完整端口检查、环境隔离和停止步骤集中在交接说明，不在这里重复。

## 接口事项怎样解释、怎样选择

以下覆盖交接说明中的五类双方待确认事项；为便于讨论，将重复/未知通知与冲突通知分开。每项建议都尚待双方确认。“代码会这样处理”不表示“机器人实际会这样发送”。

### 1. taskId：这句“完成了”究竟属于哪一单

**场景与证据。** A 取水已完成，B 取纪念品开始。此时 A 的完成通知又到达，报文仍只有“成功”，网关只能把当前 B 标成完成。这不是每次都发生，但在这个输入顺序下已有 HTTP 测试复现，本轮该复现再次通过。尚无真实机器人证据证明它会这样发送。

**要保护什么。** 保护每一单的完成事实与当前占用。B 实际还在执行时误释放，会让界面错误提示领取，甚至允许提交 C。当前单任务占用只阻止同时提交，不能识别已经结束的 A 的通知。内部任务 UUID 没有发给机器人；`requestId` 只防止浏览器同一提交重复下发，不能解决机器人通知串单。按商品和数量匹配也不够，两位访客可能下完全相同的订单。

**默认建议。** 如果旧通知可能跨单到达，建议下发携带持久化、唯一的 `taskId`，完成和故障通知原样返回，用它查找对应任务。多任务、重试、重启后的通知恢复都会增加这种需要。若只做没有历史消息的一单，或能证明旧通知绝不跨越任务边界，taskId 并非必需。受理回执在当前 HTTP 请求中已有请求关联；是否额外回显 ID 可讨论，不为凑齐字段必加。采用编号时还须确认无编号旧报文如何迁移，不能混用后仍盲目归给当前单。若以后允许下发重试，还须约定机器人对同 ID、同参数只执行一次，不能认为仅增加 ID 就自动获得这个能力。

**不改报文的替代与保证。** 对没有历史通知的首次单任务联调，可以先只做一单，异常后暂停，不立刻开放下一单。如果希望无 ID 连续运行，机器人团队须明确保证：只有我方一个发单入口；同一时刻只有一单；上一单完成、拒绝或人工收尾边界之后，不会再有它的完成/故障通知到达，包括并行在途请求、丢回执重发和重启恢复。还要说明双方如何识别这个边界、如何消除旧通知。这是一项强约束，现接口并未给出可核对的交接机制；只有“我们一般不会重发”或“多等几秒”不足以安全实施。若无法保证，保留单次联调限制，继续讨论关联方案。

**影响与会议问法。** 不阻塞明天正常模拟演示；首次真实单任务须先排除历史消息；可靠连续真实多单应有关联机制或可验证的等效隔离。“上一单结束后，会不会还有它的通知在下一单期间到达？如果不能排除，我们是否在下发和通知里带同一个任务编号；如果不带，你们怎样保证旧消息不会再来？”

### 2. 迟到、重复和未知通知：再说一遍不能变成另一件事

**场景与证据。** A 的完成已经入库，但回执在网络中丢失，机器人可能再发一次；或重启后补发旧通知。机器人是否重发、是否保留队列仍是防御假设。现有测试验证了部分同单重复通知、无任务通知和事务失败重试；跨单误结束 B 已复现。当前无 active 时完成只记录审计，故障会形成全局告警；B 已开始时，两种通知都会被当作 B 的通知。

**要保护什么。** 一次通知的重传不能重复改变任务，更不能改变另一单。无当前任务也不能一概丢弃故障，否则可能隐藏真实设备问题；有当前任务则不能把来源不明的通知直接当作当前任务事实。

**默认建议。** 关联确定后，同任务、同终态的重复通知只记录审计并返回一致回执；旧任务或未知 ID 的通知保留待核对记录，不改变当前单。未知消息成功回执可以只表示“已保存待核对”，不能说成已完成业务处理；机器人是否接受这种语义需确认。仅有一次最终结果时，任务编号加结果可能足够，不必预先再引入事件编号。

**不改报文的替代与保证。** 保持现有单任务联调，异常后暂停，逐条人工核对。要安全连续运行，需要机器人保证通知不会越过上一节的交接边界；重复通知若存在，必须在下一单开始前结束且无在途副本。现代码无法仅凭相同请求体判断重复还是新完成，不能靠我方“看到一样就忽略”。

**影响与会议问法。** 不阻塞正常模拟展示；真实单任务也可能因通知丢失而一直等待，连续任务还可能串单。“通知没收到我们的回执时，你们会不会再发？重启后还会不会补发？我们收到旧单或找不到对应单的通知时，双方怎样核对，是否需要暂停新单？”

### 3. 冲突通知：先说故障，又说完成，该相信什么

**场景与证据。** 同一单先上报机械臂故障，随后另一个发送线程又报告完成；也可能完成后才到达故障。是否真的存在多发送线程或矛盾结果尚未知，不能写成机器人已发生故障。代码可直接判断：fault 仍属于 active，随后 finished 会将其改成 succeeded 并释放；完成后 error 若此时无 active，会成为全局告警，若 B 已开始，会影响 B。本轮没有另做冲突实测，这些是代码路径分析。

**要保护什么。** 保护任务事实、故障可见性和下一单准入。不能仅按最后到达消息裁决，因为网络到达顺序未必等于事件发生顺序；也不能永久忽略后续故障，物品或设备可能确有问题。

**默认建议。** 先关联到任务，再约定终态规则。建议不直接覆盖已记录的终态，保留冲突并要求复核；冲突期间保守阻止下一单，并核对已经开始的下一单是否需现场干预。若机器人业务允许“故障后恢复完成”，应明确前一条是可恢复状态还是正式不可恢复故障；当前契约只上报不可恢复故障，不能擅自把它降格成进度。

**不改报文的替代与保证。** 机器人可以保证每单只产生一种最终结果，重传仅重复该结果，其他可恢复问题在机器人内部处理。必须覆盖异常路径、并行发送和重启，并保证任务结束后不再发送矛盾结果。若机器人能够提供并验证此保证，可暂不为假设冲突增改接口；否则需确认处理规则。无 ID 时，即使单任务不冲突，跨单关联仍须单独解决。

**影响与会议问法。** 不阻塞常规模拟演示；真实单任务的异常链路就可能受影响，并关系到下一单能否安全进入。“一单会不会先报不可恢复故障、后来又报完成？如果会，哪条才代表最终事实；在确认之前，我们是否先停住下一单？”

### 4. 回执与重发：消息已保存，不等于设备已收尾

**场景与证据。** 网关已把完成通知写进 SQLite，但成功回执丢了，机器人不知道是否收到；另一种情况是写库失败，网关确实没有保存通知。网络丢回执是需要防御的假设，未确认真实机器人有重发策略。现实现把回调审计和任务状态放在同一事务，提交后才回复成功并发布状态；既有故障注入测试验证写入失败返回非成功并回滚，成功重试及重启保留事实。本轮这些相关接口测试通过。

**要保护什么。** 保护“网关没有收到”与“已收到但回复丢了”的区别。完全不重发可能让已经完成的任务永远占用；无关联地重发又可能影响下一单。`success` 表示接口调用结果，`code=1` 不能判断成败。网关收到通知的回执更不能替代机器人已经停止的保证。

**默认建议。** 保留现稿格式，双方确认成功回执表示已持久接收。回调非成功、超时或回执丢失时，建议机器人重发同任务同结果；关联和幂等处理先达成一致，再约定次数、间隔、停止条件和重启后恢复。不是预设“必须重试五次”。当前模拟器只尝试一次回调，失败只报日志，不能拿它证明机器人重发能力。

下发指令与通知重发必须分开：机器人可能已经受理，但下发响应丢失，我方目前进入“受理不明”、保留占用，不自动重发。浏览器用原 `requestId` 核对，只返回已有任务，不再向机器人发送。若将来要重试下发，需要机器人持久去重及同 ID 参数校验的明确保证。

**不改报文的替代与保证。** 可以先维持单次通知、人工核对通知失败，不引入自动重发；机器人须能保留和展示未确认结果，发生失败时告知操作人员，异常后停止后续任务，双方人工核对真实完成/停止及旧消息清理。不能把这种人工兜底说成可靠自动闭环。若想不带 ID 又自动重发，仍须提供旧通知不跨单的隔离保证。

**影响与会议问法。** 不阻塞明天模拟主流程；真实单任务就需要确认失败怎样发现和收尾，可靠连续运行还需要与关联规则配套。“我们回复成功准备表示已经保存通知。你们遇到非成功或收不到回复时怎样处理？下发受理回复丢了时，我们先不重发，能否由你们查清是否已执行？”

### 5. 故障、长时间等待和下一单：谁确认机器人真的可以继续

**场景与证据。** 机器人说机械臂无法恢复，但物品可能还夹着；或者取物一直没有任何通知。故障上报是否意味着运动已停止、物品已放妥和设备可接下一单，文档没有保证，也没有真实联调证据。现代码 fault/uncertain 保持占用；工作人员凭据和明确确认齐备才可解除。执行中即使超过两分钟，也只提醒，接口拒绝人工解除。本轮相关既有接口测试通过。

**要保护什么。** 保护设备安全、物品去向和下一位访客的任务。直接解锁可能在前一单尚未收尾时再发新单；永久锁住又会使现场服务中断，所以需要确定负责人和实际收尾路径。taskId 能告诉我们故障属于哪一单，不能证明设备已停止或恢复可用。

**默认建议。** 故障通知不自动解锁，由人员确认停止、物品处理和设备可接单，再解除我方占用，同时清理或隔离旧通知。正常时长由机器人团队提供，我方据此调整提醒；提醒与强制结束分开。执行中静默仍联系机器人负责人，不因时间到就取消。若需要从执行中人工收尾，须先确认安全事实、旧消息边界和操作准入，再安排我方改动；今晚不开放此能力。

**不改报文的替代与保证。** 沿用现有 fault/uncertain 人工入口，机器人团队提供停止/恢复核对步骤、可确认的设备状态、物品处理办法、负责人及旧通知清理保证。若希望故障通知直接代表任务结束并允许下一单，也可以先讨论不加字段的语义约定，但对方必须保证“发送时已停止、物品已处理、已可接单、旧单消息不会误入下一单”。这属于双方对语义的确认，不能由我方宣布；设备仍故障时显然不能满足可接单保证。

**影响与会议问法。** 不阻塞已预演的模拟故障展示；真实单任务故障恢复就必须明确，连续运行更不能缺少准入条件。“故障通知发出时，机器人是不是已经停止？物品由谁处理，恢复后谁确认可以接下一单？一直没有通知时，我们现场联系谁，怎样核对并收尾？”

### 6. 地址、目录和现稿建议值：给的指令能不能被正确执行

**场景与证据。** 页面示例里的“矿泉水、货架1-2层”可能与机器人配置的物品编码、点位不一致；网关在我方机器上可访问，机器人未必能反向访问回调。实际取值和网络尚未核对，因此这是明确的配置缺口，不是已证明机器人会走错位置。正式文档已经给出三接口结构，但标明实际 URL、回调方法、通知体和回执细节待确认。

**要保护什么。** 保护任务含义和通知可达性。HTTP 成功不能证明物品对应正确；只测我方到机器人，也不能证明机器人能回调我方。配置准入为真不等于网络验证通过。

**默认建议。** 沿用现稿 POST、路径和 success 语义，先共同核对完整地址、回调可达地址、物品/点位对照和数量限制。确认完成通知采用空体、空 JSON 还是 result:success，以及故障描述与回执最终格式。当前完成入口兼容空体/空 JSON，或仅 result:success；不接受额外字段。故障描述非空且有长度限制是我方实现边界，需要实际报文核对，不自动变成双方契约。

**不改契约的替代与保证。** 路径一致而主机不同，可用已有配置接实际地址；示例目录可换为双方核对的目录，不增加查询接口。机器人团队必须提供可执行的实际取值表、对应接收端和回调来源网络条件，并确认报文可按现稿处理。若对方方法、字段或含义不同，需明确协议变更，不能靠我方猜测兼容。资料未到位时，继续用本地示例模拟，正式模式保持新发单准入保护。

**影响与会议问法。** 不阻塞本地演示；真实单任务连通与取物前必须核对。“能否给一份确实能执行的物品、位置和数量表，以及任务接收完整地址？你们从实际机器人网络能否调用我们的完成和故障地址，报文是否沿用当前稿？”

## 语音输入的可行性和回答口径

### 需求究竟确认到哪里

9 月 21 日原文在 01:22 问“语音操控的机器人”，01:38 回答“对”。因此语音是有原始会议依据的设想，不能说客户从未提出。9 月 29 日会议继续讨论自然语言交互，并在 06:03、08:41 支持照片选品和点击下发；没有明确把语音列为 10 月 12 日必交项，也没有明确撤销早期语音设想。

未注明日期的同事讨论在 16:58–20:02 提及语音输入，35:11–35:50 又说先调研、这三天可以不完整实现。它说明需求讨论过程，但不能单独决定客户验收优先级。原文路径保留在末尾，未改写原文。

本轮只读核对在线 [VLM-14](https://linear.app/sevenova/issue/VLM-14/bluesword-gateway完成兰剑展会初版系统开发与演示) 的描述及 10 月 10 日验收评论：要求核心接口、双供应商实际调用、对话式前端、必要自测和 10 月 12 日演示，没有语音条款。项目背景和当前交接也把语音排除在初版实现之外。结论是：**语音有早期需求背景，目前属于未纳入本次验收的增强需求；如果对方仍把它视为展会必备，应另行确认目标日期、设备和效果标准。**

### 浏览器原生方案：最少改哪里

当前 React 前端只有受控文字输入 `text/setText`、聊天 `chat()` 和独立确认 `submit()`，没有录音或语音识别。最小方案是在输入框旁增加默认关闭的麦克风按钮；点击后使用可用的 `SpeechRecognition` 或带前缀构造器，设置 `zh-CN`、单次识别，只接收最终文本。按钮须是普通按钮，避免误触发表单提交。

需要补充严格 TypeScript 所需的浏览器接口类型、识别实例及会话版本、录音中/结束/失败提示、停止和组件卸载清理。现有输入框禁用时，识别按钮也应禁用；提交或请求待核对期间不启动识别。识别结果只通过 `setText` 写入当前可编辑草稿，不调用 `chat()` 或 `submit()`；用户校对后点“发送需求”，得到建议后仍单独点“确认取物”。开始新体验、用户修改草稿、发送文字、提交任务或组件卸载时终止并使旧识别结果失效，避免迟到语音覆盖新输入。不支持、无声音、权限拒绝或网络失败时保留文字路径，不自动反复启动录音。

这条路径不需要新增我方后端上传接口或机器人字段。浏览器内部识别服务的网络和数据处理仍需查清，不能因为叫“原生”就承诺离线、免费或不上传。[MDN 接口说明](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition) 明示兼容性有限、部分实现依赖远端服务。[设备内识别说明](https://developer.mozilla.org/en-US/docs/Web/API/Web_Speech_API/Using_the_Web_Speech_API) 要求对应语言包；本机尚未验证中文包，不能承诺离线中文识别。

本机 Edge 155.0.4283.45 的已有探测只确认构造器、设备内识别相关属性和麦克风 API 存在。探测没有启动识别、请求麦克风或安装语言包；这不证明明天同一浏览器在真实页面、真实麦克风和现场网络下可用。本轮未重新探测，也未执行任何语音调用。

### 服务端 Whisper 等方案：增加了什么

托管转写的最小链路是“前端录制短音频 → 我方后端上传处理 → 转写服务 → 可编辑草稿”。已有聊天入口只收 JSON，不能直接接音频；须新增独立音频接收与供应商调用能力，处理大小/时长限制、格式、取消、超时、错误提示和并发限制。前端还要停止媒体轨道并释放录音资源。[OpenAI 文件转写指南](https://developers.openai.com/api/docs/guides/speech-to-text) 描述音频上传转写；[转写接口](https://developers.openai.com/api/reference/resources/audio/subresources/transcriptions/methods/create) 支持 `whisper-1` 等模型。现有文字模型或中转兼容测试不能证明音频接口可用。

托管服务需要后端专用凭据和实际音频权限，增加转写费用、上传带宽、费用限额及运行诊断。还须确定音频传给谁、是否包含旁人声音、我方是否临时落盘、何时删除，以及供应商如何处理数据。这里列的是待评估负担，没有确认任何供应商的留存规则。自部署开源 Whisper 可以减少向外部发送，但换来模型下载、推理运行时、CPU/GPU 性能、服务部署和维护；也不能省掉录音、权限、噪声和准确率验证。

### 风险和工作量要分开说

中文商品名、同音词和“一瓶/两瓶”等数量可能误识别；现场音乐、多人讲话、麦克风距离和口音会增加不确定性。原生远端识别与聊天供应商可能是两条不同服务链路，聊天能用不代表语音网络能用。权限可能被用户、Windows 或浏览器拒绝，硬件也可能被其他程序占用。后续手机远程访问还要核对页面来源、HTTPS 和浏览器支持；服务端录音路径的 `getUserMedia` 受安全上下文和权限限制，详见 [MDN 麦克风接口](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)。本机回环成功也不能推出手机局域网 HTTP 可用。

以下是按一位熟悉当前 React/TypeScript 项目的开发者估计，属于排期建议，不是已完成验证或交付保证：

| 路径 | 代码实现与可控检查 | 真实可靠性验证另算 |
| --- | --- | --- |
| 原生单次识别、只写草稿 | 约半天到一天，包含取消、迟到结果保护、错误回退和必要回归；只写按钮和成功回调可能更快，但不等于完整最小方案。 | 固定本机 Edge、麦克风和网络后，至少另留半天到一天测真实词表/数量、权限失败和噪声；中文包或远端服务不可用时，时间无法仅按前端代码量估计。 |
| 托管短音频转写 | 约两到四个开发日，覆盖录音、上传、后端限制、凭据、供应商适配、失败和取消处理。 | 至少另留一天做实际供应商、格式、网络、噪声、费用和数据处理核对；不包含账号等待、多端适配或正式部署。 |
| 自部署 Whisper | 需另行做设备与部署小实验后才能估算，不能直接沿用托管工期。 | 要验证实际机器的延迟、资源占用和运维恢复，再做同样的现场语音测试。 |

建议明天前不实现。依据不是“语音做不了”，而是当前初版没有该验收项、文字主线已有证据，语音真实权限、中文准确率、设备内语言包及现场服务均未验证，半天代码也无法替代这些检查。

会议可直接回答：“语音可以作为可选输入，把识别文字交给用户修改，后续确认流程保持一致。早期会议提过，但本次初版先交付文字流程；请确认后续是否必需、用什么设备和网络、能否联网处理音频，我们再按真实商品与数量样本评估。”

后续评估条件是确定需求日期、设备/浏览器、麦克风、真实商品词表与数量、联网和数据处理约束，再预留实际环境验证时间。无论选哪条路径，都须验证误识别能够编辑、取消后无旧结果覆盖、不点击发送和确认就零发单；未达到条件时继续保留文字和手动选择。本轮没有写语音功能、请求麦克风或执行真实语音 API。

## 会议优先问四件事

1. “上一单结束后，还会不会重发或补发它的通知？如果可能，是否用同一个任务编号关联；若不用，怎样保证旧消息不会进入下一单？”
2. “每单最终结果是否唯一？收不到我们的回执、网关或机器人重启、以及先故障后完成时，你们怎么处理，我们在什么时候暂停下一单？”
3. “故障或一直没通知时，谁确认机器人停止、物品处理和恢复可用？正常任务大概多久，现场核对联系谁？”
4. “第一轮真实单任务能否提供实际地址、物品点位和数量表，并从机器人网络验证完成/故障回调？方法和报文是否沿用现稿？”

语音在对方询问或讨论后续体验时再澄清目标日期和验收标准，不把它与今晚必须完成的代码任务混在一起。会议答复先记为待核对结论，获得明确确认后再更新协议或排期。
