Claude 分析中“会重发、会跨单重发”及“服务重启后会重发”没有当前正式文档或机器人代码证据，只能作为待确认假设；“建议 5 次、指数退避”是可讨论的策略，不能视为已经实施。当前 HTTP 替身复现能证明网关无法区分相同报文，不能证明真实机器人实际采用这种重发策略。

任务关联方向合理，但 taskId 只解决识别对应任务的问题。还需要定义合法状态变化、相同通知的重复处理、完成与故障相互矛盾时的处置，以及数据库提交失败的回执。未知标识直接回复成功可能使机器人停止重发而丢失未核对事件；只有在双方认可的持久化隔离和人工处理规则下，才可采用这种策略，不能默默忽略。

“停止重发”和“允许下一单”可以分开设计，不需要因此增加状态查询接口。但关联标识不能证明机器人已物理收尾，也不能推导并发能力。当前故障占用及人工核对规则继续保留。

需要向机器人团队确认的事项如下，此记录没有向对方发送消息：

1. 收不到回执、网络断开和机器人服务重启时，通知实际怎样重试？次数、退避、持久化和重试耗尽后的责任分别是什么？是否可能跨单到达？
2. 是否采纳我方生成并持久化 UUID、三个接口必须携带并原样回传的方案？如采纳，应明确回执字段、成功判定及无标识旧报文的处理，先更新正式文档再实施。
3. 未知标识、重复完成/故障和相互矛盾通知如何记录与回复？哪些通知可以停止重发，哪些必须进入人工核对？
4. 完成与故障分别在什么条件下允许下一单？机器人是否完成收尾、是否接受并发，不能只由网关的本地业务选择决定。

## 本阶段实际实现

**P1 已复现，尚未修复。** HTTP 测试完成 A 后提交 B，随后再次发送无标识的完成通知；B 被误标为完成。测试名称明确标记“已知限制复现，不是修复验收”。单任务占用仍不能排除跨单迟到通知。正式协议确定前，现场连续发单必须说明这一限制；人工核对不等于技术修复。

**P2 已实现并通过本地浏览器验证。** 手动改选、增减数量和确认发单会同步使旧选择建议失效；AI 返回时还检查当前占用及任务上下文。增加“开始新体验”入口，清理访客对话与选品，保留系统任务和请求恢复信息。旧体验的回复、错误及请求结束处理不能写回新体验。提交或待核对请求存在时禁用该入口。AI 建议没有发单权限，只有用户确认才调用提交接口。

**P3 已实现并通过 HTTP/SSE 与真实 SQLite 故障注入验证。** 完成/故障通知的审计、任务状态或无任务告警在同一现有 SQLite 事务内写入。提交成功后发布状态；失败回滚并沿现有 HTTP 路由返回失败，未确认的通知不返回成功回执。没有增加通用事务重试框架，也没有重试机器人副作用。重复完成或故障在同一任务上下文内验证通过，但没有关联标识时仍无法实现跨任务去重。

**P4 部分实现。** 增加 robot_receipt、robot_receipt_failed、task_transition、callback_committed 和 callback_failed 日志，包含内部任务/请求/回调标识、状态、上游 HTTP 状态、耗时或错误类别。日志中的 taskId 是内部关联标识，没有进入机器人报文。日志不输出密钥、地址、完整对话或机器人故障正文；故障正文仍按原有业务要求保存并展示。模型供应商调用日志尚待 P5 补充，当前也没有新增日志轮转或收集系统。
