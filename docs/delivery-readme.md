# BlueSword-Gateway 现场交付包

Windows 本机人工练习也可双击 `start-deepseek.cmd` 或 `start-gpt-relay.cmd`，分别读取自行配置的 `.env` / `.env.relay`。它们构建最新网页并同时启动4101主页面和4201人工工具，使用练习数据库，不能用于连接真实机器人。输入 `q` 后回车或按 Ctrl+C 停止，切换前先停止旧脚本。真实设备仍按本文的 `pnpm serve` 方式运行。

本系统接收访客的物品选择，向机器人发送取物任务，并接收完成或不可恢复故障通知。建议将本包放在与机器人同一局域网的现场电脑上运行；自己的电脑或公司闲置主机也可使用同一份包，但需要另外验证双方的网络连通。

## 安装与启动

需要 Node.js 24.13.0 或以上版本、pnpm 11.25.0。包内包含源码、锁文件和已构建网页，不包含 Node.js、pnpm 或 node_modules。首次安装需要下载锁定依赖；离线现场须事先完成安装。

先用 `node --version`、`pnpm --version` 核对环境；Node 须达到最低版本，pnpm 使用项目锁定的11.25.0，不为交付升级依赖。包内 `delivery-manifest.json` 提供打包时间、源提交及每个文件的 SHA-256；源提交后存在工作区修改时，实际交付内容以文件清单为准。

在解压后的项目根目录执行：

```powershell
pnpm install --frozen-lockfile
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Linux 上同样先安装依赖，再使用 `test -e .env || cp .env.example .env` 创建配置。不要覆盖已经配置好的 `.env`。

编辑 `.env` 后运行：

```powershell
pnpm serve
```

默认打开 `http://127.0.0.1:4100`。网页和机器人回调使用同一个端口。保持该进程运行，结束时按 Ctrl+C。修改前端源码后先执行 `pnpm build`，再重新启动；仅修改 `.env` 时重启即可。

## 联调前填写

| 配置 | 应填写的内容 |
| --- | --- |
| `BOOTH_HOST` | 仅本机使用时为 `127.0.0.1`；允许局域网机器人回调时可设 `0.0.0.0`。 |
| `PORT` | 网页及回调端口，默认 `4100`。 |
| `ROBOT_DISPATCH_URL` | 机器人团队提供的完整任务接收地址，例如 `http://<机器人IP>:<端口>/api/task/dispatch`。 |
| `BOOTH_CATALOG_PATH` | 现场物品目录；逐项核对物品名称、位置、每单上限 `maxCount` 和补满数量 `initialStock`。 |
| `BOOTH_CATALOG_CONFIRMED` | 现场目录核对完成后设为 `true`；未确认时系统禁止新发单。 |
| `BOOTH_DB_PATH` | 当前系统的数据库文件，默认 `.data/booth.sqlite`。重启时保留任务和库存，不随意更换文件。 |
| `BOOTH_OPERATOR_TOKEN` | 负责人自行设置的工作人员凭据，用于异常处理及补货重置。 |
| `BOOTH_AI_PROVIDER` 及对应模型、密钥 | 选择 `openai` 或 `deepseek`，只填写所选供应商的有效配置；密钥保留在服务器的 `.env` 中。 |

如果聊天框显示“助手暂不可用，可直接选物品”，表示运行服务没有加载到所选 AI 供应商的密钥；仍可手动选品并验证机器人接口。需要聊天时，在 `.env` 中填写 `BOOTH_AI_PROVIDER` 和对应的有效密钥、模型，再重启服务。对话中的出发、抓取、返回文字是固定模拟展示；完成由机器人回调决定，不要求机器人提供这些中间接口。

`0.0.0.0` 是监听设置。告知机器人团队的回调地址应使用运行电脑的实际局域网 IP，例如 `http://<运行电脑IP>:4100`，并实际检查机器人能访问该地址。网关也必须能访问 `ROBOT_DISPATCH_URL`，只通一个方向不能完成整单。

## 双方接口

具体协议以包内[接口文档](接口文档.md)为准。当前路径和部分报文仍是待双方确认的对接草案，联调时逐项核对。

| 方向 | 接口 | 请求内容 |
| --- | --- | --- |
| 网关调用机器人 | `POST /api/task/dispatch`，完整地址由机器人团队提供 | `{"location":"现场位置","item":"物品名称","count":1}` |
| 机器人通知网关完成 | `POST /api/task/finished` | `{"result":"success"}`；我方也接受空 JSON/空请求体。 |
| 机器人通知网关故障 | `POST /api/task/error` | `{"message":"不可恢复故障说明"}` |

机器人受理响应使用 `success:true/false`；`code:1` 不作为成功判断。受理仅代表接单，不能代替完成通知。网关完成/故障回执为 `{"code":1,"data":"OK","success":true}`。`GET /api/health` 只检查网关进程，不证明机器人在线。

当前每次只允许一项任务。受理不明和故障保持占用，工作人员须现场核对后在 `/#operations` 处理；执行中的任务不能从我方页面取消。回调尚无任务关联标识，跨单迟到通知可能误关联下一单，这个限制须在真实联调前与机器人团队核对，详见[任务关联标识说明](task-id-proposal.md)。

## 人工测试与日常补货

真实联调前按[人工测试指南](manual-interface-test.md)逐项操作并记录。人工对端只在本机工作，不会自动上报完成；它验证我方行为，不验证机器人动作。包的自动检查记录与人的操作记录分别保存。

物品选不了或不能继续加数量时，先看目录中的剩余数量和右上角状态。库存不足时限制选择，例如水初始3瓶，取完后须补货才能继续；有未结束任务或异常待核对时，也会暂停新发单。库存跨重启保留，“开始新体验”不会补满，这些限制并不表示系统出错。

工作人员打开实际网关地址加 `/#operations`，输入负责人配置的 `BOOTH_OPERATOR_TOKEN`。补货后，在“补货重置”中选择物品，核对“补满后”目标，勾选“已核对并补满所选物品”，点击“重置所选物品库存”；只恢复所选物品，保留任务记录。有未结束任务或告警时不能重置。完整步骤见[人工测试指南的工作人员操作速查](manual-interface-test.md#工作人员操作速查)。

每次成功处理后凭据会清空，补货重置后补货勾选也会取消；下次操作须重新填写并确认，按钮再次变灰是正常行为。

整批补货可在同一选择框选“全部物品”，逐项核对页面列出的补满目标，勾选“已核对并补满全部物品”，再点击“重置全部物品库存”。只有所有实物都已补满才使用此操作；系统一次恢复全部数量并保留任务记录。单个重置仍可使用，有任务或告警时两种重置都禁用。

库存按已提交数量预留，完成后不再扣一次；明确拒绝退回预留，受理不明和故障不自动补回。异常时须先核对机器人已停止及物品情况，再用“解除本地占用”处理；这不发送停止指令，也不恢复库存。补货无需点击“解除本地占用”。数量规则详见[库存说明](booth-inventory.md)。

## 运行地点的备选

现场电脑或与机器人同一局域网的公司主机可以直接按上面的 IP、端口对接。SSH 或远程桌面用于协助安装和配置，本身不会让两个网络互通。

当前公司闲置主机为 Windows 11，可通过 UU 远程操控，没有公司 VPN；这些是已知运行条件，不代表已完成安装或异地网络已打通。笔记本带到公司后，可以先按人工测试指南在其中一台机器验证，再决定正式运行地点。

如果将系统留在自己的电脑或公司主机，而机器人位于另一处网络，需要公司已有的网络通道或另行配置可供双方访问的通道。最终必须测通网关到机器人、机器人到网关两个方向，并保证运行电脑在联调期间持续在线。该网络方案尚未选定，本包不自动安装穿透工具或改变网络配置。
