# Issue tracker: Linear（自定义 / Other）

本文件是 BlueSword-Gateway 项目 Linear 使用规则的唯一详细配置来源。
Issue 书写规范仍以本文件指定的外部权威规范为准。

## 正式来源与归属

Linear 是本项目唯一正式的 Issue 管理系统。
正式 Issue 的身份、字段、状态、评论及关联以在线 Linear 为准。

- Workspace：Sevenova（sevenova）
- Team：VLM（仿真部门）
- Team ID：64679128-1a68-4d7e-9cc8-0c8d2dd3b700
- Project：不关联 Project

新建 Issue 的默认归属采用上述配置。
对既有 Issue 操作时核对其实际归属，不自动迁移到默认团队，
也不自动清除已有 Project 关联。
归属存在歧义时展示候选，请用户选择。

## 读取权限

可以自由搜索、列出和读取用户有权访问的 Linear Issue，
不需要逐次询问。优先使用已连接的 Linear 工具。

读取授权不包含写入授权。
本地历史记录可能过时，不能替代在线 Linear。

## 写入权限与确认流程

所有 Linear 写入操作必须先获得用户对具体操作的明确确认，
包括但不限于：
- 创建 Issue。
- 修改 Issue 的任何字段。
- 发布、修改或删除评论。
- 变更状态、分配负责人、修改标签或优先级。
- 建立、修改或删除 Issue 关联。
- 删除或归档 Issue。
- 创建或修改团队、Project、标签及其他 Linear 对象。

每次写入前，必须展示：
1. 目标 Issue 的标识、链接及归属；新建时展示拟定归属。
2. 具体操作，以及所有受影响字段、评论或关联。
3. 修改前后的差异；新建内容的修改前标记为“无”。
4. 完整待提交内容，包括标题、描述、每条评论及其他字段值。

等待用户明确同意后，仅执行该次确认涵盖的具体操作。
一次确认不授权未来同类操作。
批量操作必须逐项展示，授权仅覆盖用户明确确认的项目。

提交前核对目标当前内容。若当前内容或待提交内容发生变化，
重新展示差异并获得确认，不使用旧确认覆盖新内容。

提交后读取核对结果并报告。
部分失败时说明已完成与未完成操作，
不得自行提交未经确认的替代操作。

可以自行分析需求、编写草稿和提出修改建议，
但用户确认前不得向 Linear 提交。

技能中的“发布”“认领”“解决”“同步进度”等要求，
只要涉及 Linear 写入，均须遵守上述确认流程。
完成开发任务也不构成自动更新 Linear 的授权。

## Issue 书写规范

编写或修改 Issue 标题、描述、评论等内容之前，
必须先读取并遵守：

`docs/references/requirements_of_issue.md`

该文件是 Issue 书写规范的权威来源。
未经用户确认，不得修改它，不得自行简化或覆盖其要求。
本配置不复制规范正文，也不以摘要替代读取原文件。

若无法读取，报告具体路径与失败原因，暂停 Issue 内容编写，
不得猜测规范或仅凭缓存继续。
用户确认其他权威规范位置后，再重新读取并继续。

对于规范中含义或字段映射不明确的要求，先向用户澄清，
不自行推断或改写 Linear 系统元数据。

## 临时草稿与技术方案

`.scratch/<feature>/` 仅可存放临时分析、
待确认的 Issue 草稿和实施计划，不是第二套正式 Issue 系统。

临时 Issue 草稿须明确标注“待确认 / 未提交 Linear”，
不能被视为已创建的 Linear Issue。
不得长期维护 Linear Issue 与本地 Markdown 的重复副本。

复杂技术方案可独立保存为项目内的正式 Markdown 文档，
由 Linear Issue 引用。向 Linear 添加或修改引用仍须确认。
正式资料与临时资料的处理沿用 `AGENTS.md`。

技能要求“发布到 Issue tracker”时，
先准备 Linear 提交草案，展示完整内容并等待确认。
要求“读取相关 ticket”时，读取在线 Linear；
本地草稿不能替代正式 Issue 或正式状态。

## Git 代码托管边界

BlueSword-Gateway 使用独立本地 Git 仓库。当前不配置 remote、不执行 push 或远程 Git 操作。旧 BlueSword-Agent 仓库仅作为冻结原型，不推送到公司 Gitea。后续用户明确授权时再为新项目配置代码托管地址，不沿用旧仓库的预设 URL。

## 用户手动操作时

用户选择手动创建或更新 Linear 时，Codex 只整理包含字段、完整内容、验收条件和理由的草案，不代为执行。用户通知操作完成后，再按要求只读核对在线结果；发现差异先报告，不自动补写、评论或改状态。
