# 网关与机器人 HTTP 接口

现场采用机器人团队 2026-11-02 提供的 VLM HTTP v1.2。机器人负责取物和交付，网关负责对话、整单确认、发单和展示回报。

## 1. 配置与任务

```dotenv
BLUESWORD_ROBOT_MODE=lanjian_http
BLUESWORD_ROBOT_PROTOCOL=vlm
BLUESWORD_ROBOT_DISPATCH_URL=http://<机器人IP>:8080/api/task/dispatch
# 可选：留空则读取项目内 config/booth-catalog.example.json
BLUESWORD_CATALOG_PATH=
BLUESWORD_OPERATOR_TOKEN=<工作人员口令>
```

机器人侧将 `vlm.url` 设置为网关地址（例如 `<上位机IP>:8000`），两端应互相可达。不要把示例地址当成现场地址。

在 `backend/.env` 配好上述值后，从项目根目录启动网关：

```bash
uv run --locked --project backend uvicorn bluesword.app:app --host 0.0.0.0 --port 8000 --workers 1
```

机器人填写这台网关电脑的局域网 IP，不能填 `localhost` 或 `0.0.0.0`；如果选其他端口，启动命令与 `vlm.url` 一起修改。允许机器人访问该端口，并允许网关访问机器人 8080。普通模拟启动脚本仅监听本机，不能直接用于此联调。

`progress`、`finished`、`error` 三个回调不要求文档未约定的 Bearer token，即使网页 API 设置了 `BLUESWORD_API_TOKEN` 也一样；请在受控展台网络中开放回调端口。先从网关电脑查询机器人 `/api/health`，再从机器人电脑访问网关 `/health` 验证反向网络（网关配置 token 时此检查需携带它）。最后通过网页确认一单，核对真实回报、照片和最终结果。Python 自带的 `http.server` 不处理这些 POST 回调，不能代替网关验证接口成功。

物品目录的 `id` 是网关内的稳定标识；可选 `robotItem` 是机器人接受的中文名或内部编码，未配置时使用 `name`。当前目录暂沿用原有物品与编码（`robotItem` 等于原 `id`）。更换物品只需修改或替换 JSON，待任务结束并核对完毕后重启后端、刷新网页，不需要重新构建前端。同一商品的 `id` 保持不变可保留库存；不同商品用新 `id`。已有库存不会因修改 `initialStock` 自动补满。现场需核对这些暂定编码是否与机器人一致。v1.2 的 `location` 可省略，机器人目前只记录它、不以它定位。旧 v1.1 模式仍要求配置真实位置。

每单最多两件，同种两件或两种各一件；一次确认下发一条完整取送任务，不拆成取货和卸货，不按用户或会话限制总次数。请求编号用于网关重复提交去重，机器人任务编号用于关联回报。

## 2. 发单前查询

网关在实际发单前调用一次 `GET /api/health`：

```json
{"code":1,"data":"ok","success":true,"busy":false}
```

只有有效响应且 `busy=false` 才发单。无法连接或机器人忙时不下发、不预留库存，不自动排队。健康响应不能证明机器人已抓稳或已交付；不进行定时状态轮询。

## 3. 下发完整任务

```http
POST /api/task/dispatch
Content-Type: application/json
```

```json
{
  "taskId":"网关生成的唯一编号",
  "items":[
    {"item":"矿泉水","count":1,"location":"货架1-2层"},
    {"item":"shupian","count":1,"location":"货架2-1层"}
  ]
}
```

`items` 含 1～2 项，总数量不超过 2；同一种物品合并数量。机器人可能按自身优先级重新排序。`pickIndex` 表示实际执行顺序，不能按下发数组下标对应商品。

受理回复：`{"code":1,"data":"received","success":true}`；明确拒绝为 `success:false`。接单不等于完成。不明确的回复或超时不自动重发。

## 4. 进度与识别照片

机器人调用网关 `POST /api/task/progress`：

```json
{
  "taskId":"网关生成的唯一编号",
  "stage":"target_located",
  "stageIndex":2,
  "stageTotal":8,
  "pickIndex":1,
  "message":"已识别到目标（薯片），准备夹取",
  "detection":{"item":"shupian","label":"薯片","attempt":1},
  "image":{"mime":"image/jpeg","width":640,"height":400,"data":"JPEG的Base64内容"}
}
```

| stage | 意义 | stageIndex |
| --- | --- | --- |
| arrived_shelf | 到货架并完成贴靠 | 第 1 件 1，第 2 件 4 |
| target_located | 识别到目标，准备夹取 | 第 1 件 2，第 2 件 5 |
| grasped | 已抓稳，夹爪校验通过 | 第 1 件 3，第 2 件 6 |
| at_delivery | 到交付处 | 单件 4，双件 7 |
| placed | 放下本次搬运的物品 | 单件 5，双件 8 |

- `stageTotal = 3 × 件数 + 2`。取物阶段 `pickIndex` 为 1 或 2；交付阶段固定为 0。
- `message` 只用于显示，不解析其自然语言来判断成功、数量或商品归属。
- 序号允许跳跃。按 `taskId + stage + pickIndex` 更新记录；识别重试 `attempt` 更大时更新同一行及照片。重复或过期回报不重复展示。
- 照片只在 `target_located` 提供，已经带框和英文置信度。网页直接显示，并在原有说明区域显示 `detection.label`，不伪造结构化坐标、置信度或再次画框。
- 照片在内存中保留本单最新一张，以便网页重连恢复；不把 Base64 写入协议日志、SQLite 或聊天历史。网关重启后等待新的照片回报。
- 机器人按发生顺序串行发送，但回报可能丢失。`placed` 仍然只是进度，不能代替最终通知。

有效回报返回 HTTP 200；机器人不解析响应体。无效报文返回非 2xx，过期或不属于当前任务的通知返回已处理响应且不改变当前任务。机器人侧失败重试不影响其运动执行。

## 5. 完成、故障与数量核对

```http
POST /api/task/finished
{"result":"success","taskId":"同一任务编号"}

POST /api/task/error
{"message":"抓取失败","taskId":"同一任务编号"}
```

以这两类回报更新任务终态。终态之后不继续修改进度；旧任务编号不能完成新任务。超时不表示完成，现场模式没有远程停止接口。

机器人遇到无法继续的识别、机械臂或导航故障时，应携带原 `taskId` 上报 `/api/task/error`，在 `message` 中说明故障。网页保留已完成节点，单独显示红色失败记录及原因；现场人员核对机器人和物品后，通过“现场协助”恢复接单，该操作不会停止机器人或重发任务。

网页默认连续 60 秒无新进度时显示黄色“机器人状态待确认”提醒，继续等待回调，不改变任务状态、不自动重试。阈值在 `frontend/src/config.ts` 的 `progressWarningSeconds` 调整，重新构建前端生效。网关保存 `last_progress_at`，刷新页面后仍按原进度时间计时；有效的新识别尝试会更新计时，重复或过期进度不会。机器人健康检查正常也不能代替任务进度回报。

机器人文档允许双件任务在第二件失败时只送回第一件，而 `finished` 不包含结构化的实际送达清单。因此双件任务收到完成通知、但缺少两件 `grasped` 和 `placed` 回报时，网关保留“数量待现场核对”的限制；它不把缺失回报推断为失败，也不宣称两件全部送达。工作人员核对后恢复接单。未来若机器人补充实际送达清单，可据正式协议进一步精确处理。

发单前整单预留库存；明确拒单才自动退回。故障、数量不明确、超时或人工恢复接单不退库存。工作人员核对实物补满后，单独重置对应库存。

## 6. 本地模拟联调

`bash scripts/start-protocol-demo.sh --no-blender`（或不带参数）启动本机网关与 VLM v1.2 模拟机器人，默认端口 8000/8001。两端使用同一物品 JSON；覆盖单件、同种两件、两种各一件、识别重试和合成 JPEG 回报。`VLM_DEMO_SCENARIO=partial` 模拟双件只抓稳一件，`error` 模拟故障。图片和描述明确标注模拟；不连接硬件，不证明真实机器人编码或抓取能力。停止用同一脚本的 `--stop`；默认 VLM 模拟任务及库存仅存内存，重启清空。详细命令见 README。

## 7. 兼容模式

- `BLUESWORD_ROBOT_PROTOCOL=v1`：保留原 v1.1 完整任务报文 `{items:[{location,item,count}]}`，`item` 使用目录 `id`，不增加 `taskId`、`action` 或健康查询。通知无任务编号，无法可靠识别上一单迟到的通知。
- `BLUESWORD_ROBOT_PROTOCOL=progress`：保留圣涵原提案演示协议（`stage/status/detail`），用于现有模拟演示；它与机器人正式 VLM v1.2 字段不同，现场不要混用。
- 拆分技能默认关闭；VLM 模式始终使用完整取送任务。

## 网关展示与工作人员记录

普通 mock 和现场 VLM 共用物品目录，模拟库存使用独立数据库。用户确认默认等待 180 秒，继续讨论时重新计时。机器人执行默认不设总超时（`BLUESWORD_REMOTE_TASK_TIMEOUT=0`），HTTP 健康查询及接单请求仍有 8 秒超时；只按机器人最终通知更新完成结果。

通信记录在工作人员 `/operator` 页面查询、分页及下载 ZIP（CSV + JSONL），默认持久保存 30 天，可配置增加。包含请求与响应以及重复、过期、无效回报，照片内容与密钥不写入记录。`BLUESWORD_SHOW_CAMERA=false` 仅隐藏网页相机展示，不改变本文协议。
