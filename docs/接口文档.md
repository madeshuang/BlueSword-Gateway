# AI 交互系统与机器人抓取系统接口文档

> 版本：v1.0
> 更新日期：2026-10-01
> 对接草案，接口路径、回调请求体和响应示例为本稿建议，待确认。

## 1. 对接范围

展会物品及其摆放位置预先固定。用户在我方前端选择物品后，我方将目标位置、物品和数量组成一条抓取指令；机器人侧接收并执行，完成后主动通知我方。物品与位置的对应关系需确定，无需为此增加实时查询接口。

| 环节 | 发起方 | 接收方 | 预期反馈 |
|---|---|---|---|
| 下发抓取任务 | 我方 AI 交互系统 | 机器人抓取系统 | 机器人立即回复是否受理；受理不代表任务完成 |
| 任务完成通知 | 机器人抓取系统 | 我方 AI 交互系统 | 我方回复已收到通知 |
| 不可恢复故障上报 | 机器人抓取系统 | 我方 AI 交互系统 | 我方回复已收到故障消息 |

机器人执行中的导航、识别、抓取等步骤不逐项上报；我方不轮询机器人状态。可自行恢复的故障由机器人侧处理，不上报。前端在受理后显示执行中，收到完成或不可恢复故障通知后更新展示。

## 2. 接口建议

任务指令采用 **POST + JSON**。下列回调也暂按 POST + JSON 编写，具体方法和请求体待确认。路径均为本稿建议值；机器人侧提供任务接收地址，我方提供完成与故障通知的接收地址。

响应示例参考格式 `{code, data, success}`：`success` 表示本次接口调用是否成功，`data` 承载回执或故障信息；示例中 `code` 为 `1`，不据此判断成败。该格式仍需确认。

### 2.1 下发抓取任务

我方调用机器人侧提供的接口：

```http
POST /api/task/dispatch HTTP/1.1
Content-Type: application/json
```

```json
{
  "location": "货架1-2层",
  "item": "矿泉水",
  "count": 1
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `location` | string | 目标位置；示例仅用于说明，实际名称或编码及取值表待确认 |
| `item` | string | 要抓取的物品；实际名称或编码待确认 |
| `count` | int | 抓取数量 |

机器人受理后的响应示例：

```json
{ "code": 1, "data": "received", "success": true }
```

不能受理时的响应示例：

```json
{ "code": 1, "data": "<未受理原因>", "success": false }
```

我方收到受理回执后进入“执行中”；任务是否完成，以机器人后续的完成通知为准。

### 2.2 任务完成通知

机器人完成任务并放下物品后，调用我方提供的接口：

```http
POST /api/task/finished HTTP/1.1
Content-Type: application/json
```

请求体建议如下；是否需要请求体及其字段待确认：

```json
{ "result": "success" }
```

我方收到后结束当前任务的“执行中”展示，并回复接收结果：

```json
{ "code": 1, "data": "OK", "success": true }
```

### 2.3 不可恢复故障上报

机器人遇到无法自行恢复的故障时，主动调用我方提供的接口：

```http
POST /api/task/error HTTP/1.1
Content-Type: application/json
```

```json
{ "message": "机械臂故障，无法自动恢复" }
```

`message` 为机器人侧给出的可读故障描述。我方收到后展示故障信息，并回复接收结果：

```json
{ "code": 1, "data": "OK", "success": true }
```

## 3. 待确认

1. 机器人任务接收地址、我方回调地址及端口；上述路径和回调方法是否采用本稿建议值。
2. `location`、`item` 的实际取值及固定物品与位置的对照表。
3. 受理回执、完成通知、故障上报及其接收响应的最终字段和取值；完成通知是否携带请求体。
4. 是否需要为每次任务设置 `taskId`，用于将完成或故障通知与对应任务关联；如允许同时存在多个任务，还需确认并发任务的处理方式。
5. 不可恢复故障发生后，故障通知是否即视为任务结束；如长时间未收到完成或故障通知，是否需要约定超时处理方式。
